# Совместная работа над «Успеть»

## Первый запуск

```bash
git clone https://github.com/lllllllleo495/make-it-in-time.git
cd make-it-in-time
git switch dev
npm install
npm run dev
```

## Ветки

| Ветка | Назначение | Можно коммитить напрямую |
|---|---|---|
| `main` | стабильная демонстрационная версия | нет |
| `dev` | интеграция следующей версии | только небольшие безопасные правки |
| `feat/*` | новая функция | да |
| `fix/*` | исправление | да |
| `docs/*` | документация | да |

Ветку задачи создаём от свежей `dev` и удаляем после merge. Одна ветка — одна понятная задача. Для хакатона не заводим отдельные `release/*` и долгоживущие персональные ветки.

## Pull request

1. Обновить `dev` и разрешить конфликты в своей ветке.
2. Запустить `npm run lint` и `npm test`.
3. В описании PR указать пользовательское изменение, способ проверки и известные ограничения.
4. Получить просмотр второго участника, если изменение затрагивает доменную модель, MCP-контракт или алгоритм дедлайна.
5. Делать squash merge в `dev`, чтобы история оставалась читаемой.

Когда `dev` готова к демонстрации, создаём отдельный PR `dev → main` и повторно запускаем все проверки.

## Коммиты

Используем короткие сообщения в формате Conventional Commits:

- `feat: add Tutu MCP flight adapter`
- `fix: reject offers after arrival deadline`
- `docs: describe support directory`
- `test: cover impossible deadline`
- `chore: update dependencies`

Не добавляем в репозиторий `.env`, ключи, токены, `node_modules`, `dist` и локальные файлы Wrangler.

## Важные инварианты продукта

- ни один показанный вариант не прибывает позже дедлайна;
- MCP вызывается только после валидации обязательных данных;
- составной маршрут принимается только как готовое предложение источника;
- LLM не фильтрует билеты и не придумывает контакты;
- демо-данные всегда визуально отличаются от реальных;
- ошибка источника не должна выглядеть как «вариантов нет».
